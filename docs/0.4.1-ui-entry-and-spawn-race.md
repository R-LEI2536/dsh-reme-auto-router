# 0.4.1 复盘：UI 入口、row 席位、spawn 竞态

- **日期**：2026-10-02（v0.4.1 未发版内）
- **主题**：从「设置页找不到插件」一路排到「reme ready → unavailable 抖动」的三个bug
- **状态**：✅ 全部修复；`pnpm run verify` 全绿（含两个新测试套件）
- **性质**：两个是**契约误读**（UI 侧），一个是本插件自己的**并发竞态**（服务端）

## 1. 三个 bug 一览

| # | 症状（用户视角） | 根因 | 落点 |
|---|---|---|---|
| 1 | 设置页/插件页都找不到这个插件，无法配置 | volatile schema 只是**服务端契约**；Web UI 所有渲染位都是**客户端 slot 注册**，纯服务端插件没有任何入口 | 补浏览器半区：`src/client/*` + `package.json#dsh.client` + `lib/client.js` |
| 2 | 插件详情页里「包含的组件」那一行是纯文本，**点不进去** | 席位挂错：`plugins.item` 是**官方 host-plane 设置页专用**，bundle 自己的配置属于 `plugins.row.config` | `src/client/row-seat.ts`，key = `<包名>#<rowId>` |
| 3 | 设置保存成功、日志显示凭据/端点都推导对了，但 reme `ready → unavailable`，`process exited code=3` | 本插件 `ensure()` 的并发竞态：两个 reme 子进程抢同一个端口，插件只跟踪后 spawn 的那个 | `ProcessManager.spawn()` 先占位端口；`ensure()` 合并 in-flight |

## 2. 证据链（三条各自怎么定位的）

### 2.1 席位：契约原文一句话就给了答案

```
slot-contract.ts:85-86
 * package per host-plane namespace; a bundle's configuration belongs in
 * `plugins.bundle.config` or `plugins.row.config` instead.
```

`plugins.row.config` 是 **keyed slot**，key = `<包名>#<rowId>`（`config-ledger.ts:34-37` 的
`rowConfigKey`）；而 **rowId 就是 patch 行的 `id`**（`boot/plugin-manager/src/index.ts:651`
的 `rows.push({ rowId: row.id, … })`）。页面侧：注册了 key 才把那一行渲染成带箭头的按钮
（`PluginManagerPage.tsx:240-247`），点开由 `RowDetail` 渲染表单（`:506-528`）。

### 2.2 抖动：先解释「幽灵现象」，再当证据用

reme 的日志文件名是 **秒级**时间戳、且 `log_dir` 相对 cwd（`reme/utils/logger_utils.py:36-37`）。
所以**同一秒启动的两个进程会写进同一个文件**——一份日志里出现两套完整的
`Initializing ReMe Application` + 两个 `HttpService started: …port 2336`，
不是「reme 初始化了两次」，而是**两个进程**。识别出这个机制，才敢断定是双 spawn。

### 2.3 `code=3`：先排除，再承认没定论

- reme 侧：`precheck_start` 失败只是 `return`（退出码 0，`service_utils.py:123-138` +
  `reme.py:68-69`）；全量搜索整个 Python 环境**没有任何 `exit(3)`**（只有 psutil 注释里
  提过这个词）。
- DSH 侧：Linux 的 spawn runner 是 `execve` 直接变成目标进程，不会另造退出码
  （`spawn-runner.ts:150-204`）。
- 结论：3 是**那个注定要死的第二个子进程**自己的退出码；它死前的 stderr 我们以前
  不记录，所以没有痕迹。**这个具体原因至今没有正面确证**——它随竞态修复一起消失；
  现在异常退出会记录子进程输出尾部，若复现即可定位。

## 3. 修法与回归保护

- `spawn()` **在第一个 `await` 之前**把自己的端口写进 `state.json`
  （`allocatePort` 只认已写记录的端口），失败时释放占位。
- `ensure(cwd)` 用 in-flight 表把并发调用合并成一次 spawn。
- 实例**只在子进程真正存在之后**才进 live map —— 保住「启动失败不推状态卡」的既有语义
  （`tests/smoke-apply.mts` 是这条语义的边界）。
- 异常退出：记 `code=… signal=…` + 子进程输出尾部（注入的 key 打码为 `<redacted>`）；
  `done` reject 时释放端口，让下一次 `ensure()` 能重试（旧代码是静默吞掉 → 端口永久占用、
  实例永远停在 `starting`、该 cwd 再也不自动重试）。
- 反向验证：把旧顺序临时放回去跑新测试，**立刻红**——同 cwd 2 个 child、两个不同 cwd
  拿到同一个端口 45925。`tests/process-manager-spawn.mts`（10 项）由此锁住。

## 4. 可复用的经验

1. **契约文档先读，再选实现路径。** 席位、key 格式、rowId 来源全在 harness 源码里写着；
   误读的代价是一个完整迭代（浏览器半区都写完了才发现挂错位）。
2. **能推导的就别让用户填。** 用户的原话是「user-approval 只需要设置两个字段」。
   key 引用与端点从 provider 在 DSH 里的 profile 读（复用 harness 自己
   `hasProviderApiKey()` 的路径），字段数 = 用户心智负担。
3. **跨 `await` 的「检查-然后-设置」一定是竞态。** 通用修法：**reserve-before-await**
   （先同步占位）＋ **in-flight 合并**（同 key 的并发调用共用一次执行）＋ **失败即释放**。
4. **日志/文件命名会制造幽灵现象。** 秒级文件名 + 同秒双进程 = 「初始化了两次」的假象。
   先把这类机制解释清楚，再把它当作证据；否则会去改错地方（reme、key、配置全是无辜的）。
5. **「测试能红」比「测试能绿」更能证明修复有效。** 每修一个竞态，都用旧顺序跑一遍新测试。
6. **既有测试是语义边界，不是障碍。** 第一版修复（实例也提前进 map）立刻打破
   `smoke-apply` 的「启动失败不推卡」，改成「只占位端口」才两全。
7. **修 bug 时顺带补诊断盲区。** 不记录子进程输出，就得靠猜退出码；现在一行尾部输出
   就够下次定位（且注入的 key 自动打码，不破坏「绝不记录 key」的约定）。
8. **区分环境噪声与代码缺陷。** 本次噪声：工作区 `.env` 的 `load_env(override=True)` 会
   覆盖注入值、前几轮遗留的**无主 reme 进程**占着端口、多进程日志交错。先分类再动手。
9. **验收标准要在动手前问清。** 「入口在哪、几个字段」这类问题返工成本极高；
   `settings.section` 是否要做、`plugins.item` 该不该用，都值得先问一句。
10. **状态要显式。** 计划模式进/不进、当前在验证什么，一句话讲清，比让协作者猜便宜得多。

## 5. 已知边界（本期不做）

- **工作区 `.env` 的覆盖风险仍在**（scope A 之外）：cwd 往上 5 层内若有含 `LLM_*` 的
  `.env`，reme 的 `load_env(override=True)` 仍会覆盖注入值。
- **残留进程**：竞态期间产生的无主 reme 仍在跑；它们 cwd 相同，可能被
  `ManualInstanceAdopter` 认领为 adopted（`adoptManual: true`），属预期行为。
- `code=3` 的正面归因（见 §2.3）：等下一次诊断输出。
